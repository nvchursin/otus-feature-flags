# Декомпозиция сервисов

## Возможности и поддомены

### Core

- Вычисление значений флагов для пользователя: стабильный хэш, batch по тегу.

### Supporting

- Управление конфигурацией флагов через админку (crud)
- Версионирование изменений и audit-log
- Распространение снапшота актуальной конфигурации флагов

### Generic

- Авторизация (oauth2)
- Мониторинг изменений конфигурации
- Аналитика использования флагов

## Границы сервисов

### ff-crud

**Ответственность:** источник правды для конфигурации, отвечает за хранение и изменение флагов

**Владение данными:** бд с флагами и всеми относящимися к ним данными

### ff-evaluator

**Ответственность:** быстрое вычисление значений флагов для пользователя

**Владение данными:** in-memory кеш (копия снапшота)

### ff-distribution

**Ответственность:** распространение снапшота актуальной конфигурации флагов через cdn и объектное хранилище

**Владение данными:** нет

### ff-consumer sdk

**Ответственность:** предоставление клиентского api для работы с флагами, инкапсулирует локальное кеширование значений и логику применения дефолтных значений

**Владение данными:** локальный кеш флагов и дефолтные значения флагов в коде

## Проверка сплочённости и связанности

### Высокая сплочённость

- `ff-crud`: всё про запись, изменение флагов и хранение актуальной конфигурации. Меняется по одной причине: новые правила управления флагами.
- `ff-evaluator`: всё про вычисление значений флагов для пользователя. Меняется по одной причине: новые правила вычисления.
- `ff-distribution`: всё про распространение снапшота флагов. Меняется по одной причине: механизм доставки.
- `ff-consumer sdk`: всё про доступ к флагам на клиенте, и их кеширование. Меняется по одной причине: поведение при недоступности.

### Риски связанности

#### Риск 1

Сервис `ff-evaluator` мог бы читать флаги напрямую из базы данных `ff-crud` (или через его api). Тогда write- и read-контуры оказываются связаны, что существенно понижает устойчивость системы к изменениям и её надёжность в рантайме.

Решение:

- сервис `ff-crud` предоставляет версионированное api для экспорта полного снапшота конфигурации;
- сервис `ff-distribution` забирает снапшот через вызов api и складывает в облачное хранилище;
- сервис `ff-evaluator` подтягивает снапшот в собственный in-memory кеш.

Таким образом `ff-evaluator` зависит только от схемы снапшота, а не от схемы бд или доступности `ff-crud`.

#### Риск 2

Потребитель завязывается на формат ответа `ff-evaluator`.

Решение:

- сделать формат ответа версионированным (`api/v1/flags`).

## Dependency Inversion

(См. Риск 1)
Инверсия достигается за счёт того, что обе стороны зависят от версионированной схемы снапшота:

- `ff-crud` не пушит данные в `ff-evaluator` и не навязывает ему схему бд с флагами, он просто публикует снапшот согласно контракту;
- `ff-distribution`: механизм доставки можно поменять, контракт снапшота останется прежним;
- `ff-evaluator` знает только про схему снапшота и умеет забирать его из любого источника.

Изменение схемы бд или недоступность `ff-crud` не затрагивают `ff-evaluator`, потому что все зависимости направлены на контракт, а не на конкретную реализацию.
