# Хранилища, шарды и реплики

## Шаг 1. Наборы данных: хранилище, согласованность, кеш

| Набор | Хранилище | Согласованность | Кеш | Как растёт |
| --- | --- | --- | --- | --- |
| D1. Флаги и версия | MongoDB | ACID: изменение и версия атомарны | Снапшот в evaluator | С числом флагов и сегментов |
| D2. Audit-log | MongoDB | Атомарно с изменением флага | Нет | Запись на каждое изменение |
| D3. Снапшоты | Object storage + CDN | Eventual consistency, ≤ 60 с | Полная копия в памяти evaluator | С размером D1 |
| D4. Значения флагов | Локальное хранилище | При сбое допустимо устаревание | Последние значения или дефолты | С числом запрошенных флагов |
| D5. Ключи идемпотентности | Redis | Повтор возвращает прежний результат | TTL 24 ч | Ограничены окном TTL и потоком изменений |

## Шаг 2. Шардировать или нет

Растут D1 и D2. Рост аудитории не создаёт персональных записей в БД: назначения вычисляются стабильным хешем пользователя и флага.

| Ступень | Решение для проекта |
| --- | --- |
| Индексы | Для флагов уже есть индексы по `_id` и уникальному `key`; индексы аудита выбираем по его запросам |
| Кеш | 10 000 RPS обслуживает evaluator из памяти, без запросов в MongoDB |
| Реплики чтения | Для вычислений не нужны: каждый evaluator содержит полный снапшот |
| Мощнее узел | Для роста записи и объёма сначала проверяем ресурсы БД и архивируем аудит |
| Шарды | Подтверждённого предела одной БД нет |

**Шарды не вводим:** масштабируем evaluator, архивируем аудит. Разделение флагов усложнит полный экспорт и транзакции с общей версией.

**Сигнал к пересмотру:** после оптимизации p99 CRUD устойчиво превышает **1000 мс** из-за БД либо свободное место падает ниже **20%** после архивирования.

## Шаг 3. Репликация и карта шардов

Три узла replica set в разных зонах, подтверждение записи большинством и резервные копии.

| Набор | Запись | Чтение | Почему |
| --- | --- | --- | --- |
| D1, D2 | Primary MongoDB | Primary; экспорт согласованной версии — транзакцией | Изменения, версия и аудит не должны расходиться |
| D3 | Один активный distributor | CDN → память evaluator | Допустима задержка распространения ≤ 60 с |
| D4 | SDK | Локальный кеш | Работа при недоступности evaluator |
| D5 | Primary Redis | Primary Redis | Проверка на отстающей реплике может пропустить дубль |

`ff-crud` и `ff-evaluator`: минимум по две реплики за балансировщиком; `ff-distributor`: один активный экземпляр с перезапуском. Redis: primary + replica.
