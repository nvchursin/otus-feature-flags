# Изменяемость архитектуры

## Изменение 1. Добавить контекст пользователя

Контекст содержит атрибуты пользователя (например регион и язык), и позволяет задавать правила вроде «включить флаг только для пользователей из региона `ru`».

| Поле | Значение |
| --- | --- |
| Что меняется | В модель флага добавляются сущность «ограничение» (constraint), а запрос на вычисление принимает контекст пользователя |
| Кто инициирует | Продуктовая команда |
| Вероятность | Высокая: избирательный таргетинг — весьма типичная функция сервиса фича-флагов |
| Чем меряем | Число затронутых модулей |

### Какие модули затрагиваются

1. **admin spa** — редактор ограничений и их валидация.
2. **ff-crud** — модель хранения, административный api и формирование снапшота с ограничениями.
3. **ff-distributor** — версия контракта схемы снапшота.
4. **ff-evaluator** — интерпретация и применение заданных ограничений до выполнения процентной раскатки.
5. **ff-consumer sdk** — передача контекста пользователя в запросе на вычисление.

Затрагиваются **5 модулей**.

### Точка расширения

Точка расширения размещается в `ff-evaluator`: вычисление должно зависеть от интерфейсов, а не от конкретных операторов.

Сценарий, под который ставится точка расширения: в будущем потребуется добавить новые форматы ограничений и операторов (диапазон чисел, даты, и т.д) или новый тип ограничения без изменения основного конвейера вычисления.

## Изменение 2. Ускорить доставку конфигурации до нескольких секунд

Меняем polling раз в 30 секунд на события о публикации снапшота через брокер сообщений, сохраняя снапшот в объектном хранилище.

| Поле | Значение |
| --- | --- |
| Что меняется | Механизм обнаружения новой версии снапшота: polling заменяется событием о публикации |
| Кто инициирует | Продуктовая или эксплуатационная команда |
| Вероятность | Средняя: текущая задержка укладывается в требования до одной минуты, но может стать недостаточной |
| Чем меряем | Число затронутых модулей и p99 времени от сохранения флага до применения новой версии |

### Какие модули затрагиваются

1. **ff-distributor** — после успешной публикации отправляет событие с версией и адресом снапшота.
2. **ff-evaluator** — подписывается на события брокера и загружает указанную версию снапшота.
3. **Infrastructure** — добавляются брокер, настройки доступа, метрики очереди.

Затрагиваются **2 модуля** и инфраструктурный контур.

### Точка расширения

Точки расширения размещаются на границах доставки:

- `ff-distributor` публикует снапшот через абстракцию `ISnapshotPublisher` и отдельно сообщает о новой версии через `IVersionNotifier`;
- `ff-evaluator` получает сигнал через `IVersionSource`, а содержимое через `ISnapshotSource`.

Сценарий, под который ставятся точки расширения: в будущем потребуется заменить технологию брокера или объектного хранилища без изменения бизнес-логики сервисов. Интерфейсы `IVersionNotifier` и `IVersionSource` изолируют брокер, а `ISnapshotPublisher` и `ISnapshotSource` — хранилище снапшотов.

## Выводы

- Первое изменение затрагивает почти весь вертикальный срез и является главным риском изменяемости. Его следует локализовать версионированной схемой снапшота и расширяемой моделью ограничений.
- Второе изменение ограничено узлом доставки конфигурации. Интерфейсы и адаптеры позволяют заменить транспорт прозрачно для бизнес-логики.
