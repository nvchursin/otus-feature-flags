# Синхронные и асинхронные взаимодействия

## 1. Сценарии

- **Вычисление флагов:** sdk запрашивает значения у `ff-evaluator`. Пользователь ждёт ответ.
- **Изменение флага:** администратор сохраняет изменение через `ff-crud`. Пользователь ждёт подтверждение.
- **Распространение конфигурации:** `ff-distributor` публикует новый снапшот, `ff-evaluator` обновляет кеш. Пользователь не ждёт.

## 2. Выбор sync или async

- spa → `ff-crud` — **sync**, нужен результат сохранения.
- sdk → `ff-evaluator` — **sync**, значения нужны сразу.
- `ff-distributor` → `ff-crud` — **sync polling**, фоновый worker периодически запрашивает версионированный снапшот и при появлении новой версии публикует его.
- `ff-evaluator` → cdn — **async polling**, кеш обновляется независимо от запросов.

## 3. Оркестрация

Api gateway направляет синхронные запросы к `ff-crud` и `ff-evaluator`, а `ff-distributor` работает независимо. Как таковой оркестрации в системе нет.

## 4. Контракт endpoint

### `POST /api/v1/flags/evaluate`

Вычисляет значения флагов для пользователя. Версия контракта передаётся в url (`v1`). Запрос и ответ используют `Content-Type: application/json`.

Поля запроса:

- `user_id: String` — идентификатор пользователя
- `environment: String` — окружение, например `production`
- `flag_keys?: String[]` — ключи флагов
- `flag_tags?: String[]` — теги флагов

Пример запроса:

```json
{
  "user_id": "user-123",
  "environment": "production",
  "flag_keys": ["new-checkout"]
}
```

Поля успешного ответа:

- `flags` — обязательный объект, где ключ — имя флага, а значение — вычисленное логическое значение.
- `config_version` — обязательное целое положительное число, версия снапшота, использованного при вычислении.

Успешный ответ — `200 OK`:

```json
{
  "flags": {
    "new_checkout": true
  },
  "config_version": 42
}
```

Ошибки:

- `400 Bad Request` — ошибка валидации запроса
- `404 Not Found` — окружение или флаг не найдены
- `503 Service Unavailable` — нет доступного снапшота.

В рамках `v1` разрешены только обратно совместимые изменения (например добавление необязательных полей). Для ломающих изменений создаётся новая версия (`/api/v2/...`).

## 5. Защита от дублирования запросов

Повторный запрос может создать лишнюю версию конфигурации и запись в audit-log. Поэтому клиент передаёт сгенерированный `Idempotency-Key`, а `ff-crud` сохраняет результат первого запроса и при повторе с тем же ключом возвращает его, не выполняя изменение повторно. Результат хранится в кеше 24 часа.
